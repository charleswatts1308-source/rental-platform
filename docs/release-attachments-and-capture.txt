Write it here: TEARDOWN BY ____________________

WHY IT EXISTS
  Our existing signature middleware reads FLAT top-level
  timestamp/token/signature fields (the inbound-routing shape).
  Delivery events NEST those inside a `signature` object — CONFIRMED
  23 Aug, no longer inferred. VerifyMailgunSignature returns 406 on
  every failure path including "Missing signature fields", and Mailgun
  treats 406 as a deliberate refusal and never retries. So events would
  be discarded permanently and silently while the webhook looked
  healthy. (A 500 would at least have given 8 hours of retries and a
  chance to notice.)
  The shapes question is therefore SETTLED. What this run still buys:
  the actual field names and structure to build the receiver against,
  and — see below — proof that the correlation key survives the trip.

CORRELATION — already in main, nothing to do here
  Every outbound letter now carries its case_message id as a Mailgun
  custom variable (commit a70065b, CaseNotice::headers()). Mailgun
  echoes custom variables back on every event, which is what lets a
  bounce be matched to the letter that caused it.
  Recipient plus timestamp CANNOT do that: the same landlord address
  legitimately receives several letters across the ladder, and a
  suppressed address raises events for sends never transmitted.
  WHAT TO CHECK IN THE CAPTURED PAYLOAD: a `user-variables` block
  carrying case_message_id. If it is ABSENT, Symfony's Mailgun
  transport is not passing X-Mailgun-Variables through and the
  correlation needs a different mechanism — worth knowing now rather
  than after the receiver is built on it.

          so this send is DROPPED BEFORE ANY DELIVERY ATTEMPT. Our API
          call succeeds, we record a letter sent, nothing is
          transmitted, and nothing ever will be.

       the ladder ratcheting on the strength of it — the record would
       assert a landlord ignored notices they were never sent.
       Missing this send means running the whole exercise twice.

[ ] 3. Raise a case to an inbox you control
       -> should produce a delivered event
       This is the CONTROL. Without it you cannot distinguish a bounce
       from a webhook that never fired at all.

WHAT WE LEARN
  The nested-vs-flat question is already SETTLED (confirmed 23 Aug) —
  events nest the signature, our middleware 406s on that, and Mailgun
  never retries a 406. A second middleware IS necessary.
  So what this run is actually for:
  - the real field names and structure, to build the receiver against
    observed bytes rather than a description
  - whether user-variables comes back carrying case_message_id, which
    decides whether the correlation key works at all
  - what a SUPPRESSED-address send looks like versus a fresh bounce —
    the two must be distinguishable, because they need different
    responses and the second is the state real cases are already in

WHAT A DETECTED BOUNCE SHOULD DO  (agreed 23 Aug, shapes the receiver)
  A bounce is not a variant of silence, it is the opposite, and calls
  for the opposite response. Silence escalates. A bounce must STOP the
  ladder and hand the problem back to the tenant — no amount of
  escalation reaches an address that does not work. The contact_failed
  status planned for #25 is the right shape.
  KNOWN GAP: there is currently NO WAY for a tenant to supply a
  corrected address (#24 — no edit route after the first letter; only
  recovery is abandon and re-raise). So contact_failed as specified
  would leave the tenant informed and powerless. The correction path
  may need to land WITH #25 rather than after it. Unresolved.

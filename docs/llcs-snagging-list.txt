LLCS SNAGGING LIST
==================

Minor bugs and rough edges spotted while testing the Landlord Contact Service
UI. These are deferred on purpose - none are blockers. They'll be fixed in a
batch once the whole LLCS lifecycle has been walked through, so testing isn't
interrupted.

If something actually BLOCKS testing (a crash, a 500, data loss, a broken
flow), don't park it here - flag it straight away.

To add a snag: copy the dashed block below, fill it in, leave Status as "open".
Severity guide: cosmetic = looks off / minor = awkward / functional = wrong.

TWO SECTIONS (added 2026-09-12)
-------------------------------

number are ones NO CUSTOMER EVER SEES: dev tooling, test-suite
weaknesses, internal docs, latent schema traps. They are real and they

#18
[SECTION 2 — DEV-FACING ONLY]
Page:        Migrations — implicit ON UPDATE CURRENT_TIMESTAMP trap on
             NOT NULL TIMESTAMP columns sitting FIRST in their table.
Severity:    minor — latent landmine; dormant on insert-only tables.
Saw:         Audit (2026-06-07, prompted by the magic_login_tokens Q1
             finding) of every CREATE TABLE migration. On MariaDB with
             explicit_defaults_for_timestamp=OFF (gafol/prod default),
             the FIRST timestamp column in a table, if NOT NULL with no
             explicit default, is silently given DEFAULT CURRENT_TIMESTAMP
             ON UPDATE CURRENT_TIMESTAMP — so any UPDATE to the row
             rewrites that column to now() (and the value lands in the DB
             session TZ, hence the "+1h" BST gap seen on magic links).
             Four tables carry the same first-column trap, all currently
             insert-only so the trap is unexercised:
               - page_views.view_date_time
               - error_logs.error_date
               - file_attachments.uploaded_date  (drop_rentals migration;
                 may not be migrated on prod yet)
               - silence_shadow_log.swept_at      (evidential log — would
                 corrupt swept_at if a shadow row is ever updated)
             Safe (verified, no action): reply_tokens (issued_at is
             useCurrent → explicit default, expires_at is nullable and
             not first), cases/case_events/case_messages/contact_messages
             (first timestamp is nullable or useCurrent), and every
             ->timestamps()/nullable() column.
Expected:    No table relies on the implicit ON UPDATE; first timestamp
             columns are either DATETIME or carry an explicit default.
Status:      open — fixed for magic_login_tokens only (Q1, this commit:
             expires_at → dateTime). The four above left as-is; flagged
             so a future UPDATE path on any of them doesn't silently
             corrupt the column.
Notes:       Invisible to the test suite — SQLite has no ON UPDATE
             CURRENT_TIMESTAMP semantics, so these only bite on MariaDB.
Fix:         Per table, switch the offending column to dateTime() (never
             receives the implicit clause) or give it an explicit default;
             since these are pre-flip, a migrate:fresh re-applies the
             amended migration on gafol (same path as the Q1 fix).

Page:        Inbound enquiry forward — the header block's SPF / DKIM line
             (ForwardInboundEnquiry). Found 2026-09-19 by Charlie on the
             FIRST live send of the stage 1 enquiry channel.
Severity:    cosmetic, but it defeated the only purpose of the line.
Saw:         Every real forward read "SPF / DKIM: ? / ?". The line exists
             so a doubtful enquiry can be judged — a landlord claiming to
             be someone, a request to remove a case — and it reported
             nothing at all. Three live sends, three identical "? / ?".
Expected:    The verdicts Mailgun actually carries, or an honest
             statement that none arrived.
Status:      FIXED 19 Sep 2026, same day, on feature/inbound-enquiries
             before merge. Suite 877 green (873 before, 4 added).
Notes:       ROOT CAUSE, and it is the interesting part: the code read
             two TOP-LEVEL payload keys, X-Mailgun-Spf and
             X-Mailgun-Dkim-Check-Result. Mailgun does not send them
             there — the verdicts live inside message-headers, a JSON
             array of [name, value] pairs.
             WHY THE SUITE DID NOT CATCH IT: the fixture invented the
             same two top-level keys, so the tests and the bug agreed
             with each other. A payload shape written from ASSUMPTION
             rather than from observed bytes. That is precisely the
             failure docs/mailgun-delivery-event-payloads.md was written
             to prevent for #25, and it recurred four days later in a
             different file.
             GENERAL LESSON, worth more than this snag: a test fixture
             for a third-party payload is a claim about someone else's
             system. It proves nothing unless it came from a real
             capture. Green tests over an invented fixture are
             self-agreement, not evidence.
Fix:         authResult() now looks in three places, cheapest first:
             the top-level keys (in case a future payload carries them),
             then message-headers for Received-SPF /
             Authentication-Results / DKIM-Signature, then "not
             reported" — which is honest, where "?" was not. A bare
             DKIM-Signature with no verdict reads "Signed (unverified)"
             rather than claiming a pass. Four tests added against the
             real payload shape, including a malformed message-headers
             value.
             CONFIRMED LIVE 19 Sep 2026, 15:04, on production: a real
             enquiry to landlord-enquiries@ read "SPF / DKIM: Pass /
             Pass". So the shape is now proven against this account's
             own bytes, not against documentation — which is the
             standard this snag exists to insist on.

#30 — CHEAP FIX SHIPPED 20 Sep 2026 (the entry above remains the
record of the August decision, which this DEPARTS FROM deliberately).

DECISION REVISED 20 Sep 2026 by Charlie: "keep it simple until volume
dictates otherwise, especially as we have new mechanism." The 1 Aug
decision was option (b), a real two-way threaded conversation. That is
NOT built and is not scheduled. What changed since August is that the
enquiry forwarder now exists, so the cheap option buys most of the
value without the threading.

WHAT WAS WRONG, both halves failing SILENTLY:
  (a) store() wrote a contact_messages row and did nothing else. No
      mail, no notification. The only way to learn a message existed
      was to log into admin and look — while the user had been told on
      screen "Your message has been sent. We will get back to you
      soon." That promise was kept only by Charlie's memory.
  (b) the admin reply sent from noreply@renters.rent with NO Reply-To.
      The apex has no mailbox, so a user who read the answer and hit
      Reply was writing into nothing. Their follow-up vanished and
      neither side found out.

WHAT WAS BUILT (3 changes, no schema, no migration):
  1. ContactMessageReceived — a notification to the mailbox in
     enquiries.forward_to. REPLY-TO IS THE USER, which is the whole
     mechanism: answering from an ordinary mail client reaches the
     person who wrote in. From is info@<inbound domain>.
  2. ContactReply now sends from info@<inbound domain> instead of the
     dead noreply@. A user's reply therefore lands on an address the
     enquiry forwarder RECOGNISES, reaches the webhook, and is
     forwarded on. The conversation continues through the mechanism
     built for landlord enquiries rather than through new threading.
  3. App\Support\ServiceAddress — one place that answers "what address
     does renters.rent send as, speaking for itself", derived from the
     inbound domain so it is always one the forwarder recognises.

ORDER INSIDE store(): the row is written FIRST, the notification is
best-effort after it. A mail failure must never cost us the message.

ACCEPTED COST, stated so it is not rediscovered as a defect: Charlie's
REPLY lives in his mailbox and NOT on the platform. Only the user's
original message is a row. Same trade as the stage 1 enquiry forwarder.
If volume ever justifies a real thread, the case token machinery
({token}@ binding inbound mail to a record) is what it would reuse.

STILL OPEN under #30: the one-shot guard on admin replies (the
controller refuses a second reply) is untouched and now slightly
misleading, since the conversation can continue by email outside it.
Harmless; note it before anyone reads the guard as the whole story.

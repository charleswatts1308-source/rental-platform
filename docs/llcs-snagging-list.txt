LLCS SNAGGING LIST
==================

Minor bugs and rough edges spotted while testing the Landlord Contact Service
UI. These are deferred on purpose - none are blockers. They'll be fixed in a
batch once the whole LLCS lifecycle has been walked through, so testing isn't
interrupted.

If something actually BLOCKS testing (a crash, a 500, data loss, a broken
flow), don't park it here - flag it straight away.

To add a snag: copy the dashed block below, fill it in, leave Status as "open".
Severity guide: cosmetic = looks off / minor = awkward / functional = wrong.

#4
Page:        Case reference (system-wide: dashboard, notification emails, URLs)
Severity:    Low — cosmetic/UX; not blocking. Pre-flip change, zero migration cost.
Saw:         Case reference is a 12-char mixed-case random string (e.g. Bmjomam2aaSV).
Expected:    Short, human-quotable reference: 6 uppercase chars, human-safe alphabet,
             case-insensitive, random, unique, never reused.
Status:      Open — design decided, ready for CC.
Notes:       Use case is a tenant quoting the reference to a landlord verbally/in
             writing ("re: case TRE3YU"), so it must survive being said aloud and
             retyped. Security is NOT carried by the reference — per-tenant login +
             server-side ownership checks already gate case access, so the reference
             can be short without weakening anything. Random (not sequential) so it
             leaks neither case volume nor allows walking. Only preprod seed data
             exists, so this is a free change now; would be costly post-go-live.

#8
Page:        System-wide — outbound mail delivery status
Severity:    Medium — evidential blind spot. Capability gap, not a defect.
             Post-cutover feature, not part of the silence-model rewrite.
Saw:         The platform records a letter as sent (frozen in case_messages,
             accepted by Mailgun) but has no knowledge of whether it was
             delivered. Evidenced 2026-06-06 on gafol: 10 sends accepted,
             4 failed at Gmail with 550 spam blocks — the system showed no
             trace; only a human reading the Mailgun dashboard found out.
             (Sandbox-domain reputation caused the failures — production's
             DMARC-aligned mg.renters.rent won't fail at that rate — but
             the blind spot exists regardless of rate.)
Expected:    Platform consumes Mailgun delivery webhooks (delivered /
             failed / bounced events), stamps delivery status on the
             case_messages row, and surfaces failures to the tenant
             ("your letter could not be delivered to <address>") with a
             path to act (correct the address, resend).
Status:      open — post-cutover feature. Design needed (webhook endpoint
             reuses the existing HMAC-verified inbound pattern; new
             delivery_status + delivered_at columns; tenant notification
             on hard failure).
Notes:       For a service whose promise is "your landlord was notified,
             here's the proof", sent-but-not-delivered is the one
             discrepancy that must never be silent. 2026-06-06 test data:
             40% silent loss on a reputation-damaged domain.

Severity:    minor — corrupts shadow-report storytelling, no data loss.
Saw:         silence_shadow_log is not in DevReset::TABLES, so
             dev:lifecycle's reset preserves yesterday's shadow rows.
             Today's reseed reuses case IDs 1..8; silence:shadow-report

             slug for N, producing a confusing report that looks like
             today's sweep walked multiple dates.
Expected:    dev:reset wipes silence_shadow_log alongside the other
             transactional tables; a fresh dev:lifecycle yields a
             shadow report that contains only today's rows.
Status:      open — scheduled: Phase 3 ride-along (per design update §6)
Notes:       Confirmed 2026-06-07 gafol live-fire: yesterday's three
             pretend probes (06-21, 07-01, 07-11) survived overnight,
             merged into today's 07-11 swept_at group, and inflated
             COUNT to 12 against an actual 6 cases swept once.
Fix:         Add 'silence_shadow_log' to DevReset::TABLES (constant
             at top of the class). One-liner, no migration.

#10
Page:        silence:sweep summary line (SilenceSweep.php:117-137).
Severity:    cosmetic — count display only; underlying rows correct.
Saw:         Re-tally filters `swept_at = $now AND is_pretend = $isPretend`.
             For pretend mode, $now is the deterministic
             `pretend_today 09:00:00`, so two pretend sweeps on the
             same date share a swept_at. The second sweep's summary
             counts BOTH runs' rows (e.g. 12 verdicts reported for 6
             cases × 2 invocations).
Expected:    Summary counts only rows written by the current
             invocation.
Status:      open — scheduled: Phase 3 ride-along (per design update §6)
Notes:       Cosmetic — every individual shadow row is correct and
             carries its own swept_at + pretend_today + verdict.
             Only the operator-facing summary tally inflates.
Fix:         Track the row IDs written this invocation (collect from
             writeShadowRow / writeExceptionShadowRow returns) and
             tally from those, instead of a swept_at re-query. Or
             switch swept_at to the real wall-clock even on pretend
             runs and keep pretend_today as the only horizon column.

#11
Page:        Stage 2+ escalation letters (click path + sweep path).
             Render path issue, not seed data.
Severity:    minor — pre-existing UX/evidential, not a 2b regression.
Saw:         Letters rendered "My description of the issue:" followed
             by an EMPTY value on every stage past the first send.
             Confirmed on gafol stage-2 auto-escalation 2026-06-07.
Expected:    A meaningful issue description on every escalation
             letter (the landlord-facing record is supposed to remind
             them what the case is about, every time).
Status:      closed — superseded by D9 (cases.description fixed at
             creation, immutable, on every outbound). Fix lands in
             Phase 3 implementation.
Notes:       Root cause: SendCaseNotice::execute's $tenantStatement
             defaults to null, and both subsequent callers pass null:
             - CaseController::sendNext (line 87) — tenant click.
             - SilenceSweep::handleCase (line 200) — auto-escalation.
             Only first-send (create-case form line 245-250) passes
             the tenant's typed description. case_messages.tenant_
             statement is per-message; cases table has no description
             column. So there is no current source for stage 2+.
             Design doc lists {{issue_description}} as a whitelist
             placeholder but does not specify a source for sweep /
             click escalation rounds.
Fix:         D9 picks option 2 (persist on case): add cases.description,
             populate at case creation, pull on every send across both
             click and sweep paths. Tenant-reply path (D8) also uses
             the same source. Implementation in Phase 3.
